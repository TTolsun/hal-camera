# Baseline 집합 비교 설계와 후보 검토 (2026-09-28)

[이슈 #165](https://github.com/TTolsun/hal-camera/issues/165)의 네 가지 문제에 대한 결정과 그 근거를 기록합니다. 결론은 다음과 같습니다.

1. baseline을 run 하나가 아니라 정상 run 여러 개의 집합으로 바꾸고, 지표마다 집합의 범위를 벗어난 경우만 판정합니다.
2. launch 사이클의 양 끝을 보는 지표 두 개(1.9 first open, 1.10 open max)를 추가합니다.
3. 녹화 지표 3.1과 3.6의 기준값은 바꾸지 않습니다.
4. launch 모드가 바뀌는 원인은 이번 변경과 분리해 별도 이슈에서 계측합니다.

회귀 규칙은 `regression-rule-v3`입니다. 판정 방법은 [PLAN 7.1.1](../PLAN-BenchMarker-v0.3.md)에, 새 지표의 정의는 [METRICS.md 1절](../METRICS.md)에 있습니다.

## 자료와 한계

[#123](https://github.com/TTolsun/hal-camera/issues/123)에서 잰 Galaxy S25+ 유효 실행 40회(0.13.2 release, `camera2-standard-v2`, camera 0)를 썼습니다. 새로 측정하지 않았습니다. 이 자료는 후보 설계를 고르는 데만 썼고, 규칙의 기준값은 하나도 이 자료에 맞춰 바꾸지 않았습니다. 새 지표 두 개도 1.1과 같은 규칙(15 %, 10 ms)을 씁니다.

설계가 실제로 맞는지는 새 측정으로 확인해야 합니다. 이 문서의 "남은 확인" 절이 그 계획입니다.

## 결정

### 1. launch 두 모드: baseline 집합으로 흡수합니다

S25+ 정상 run의 launch는 느린 모드(1.1 open 약 10 ms, 1.3 약 260 ms)와 빠른 모드(약 4.5 ms, 약 170 ms)로 나뉩니다. baseline이 run 하나이면 그 run이 어느 모드였는지에 따라 이후 판정이 뒤집혔습니다. 빠른 모드 run이 baseline이면 정상 run이 100 % 저하로 표시되었습니다.

baseline을 정상 run 집합으로 두면 두 모드가 모두 집합의 범위 안에 들어갑니다. 저하는 집합에서 가장 나쁜 값보다 규칙만큼 더 나쁠 때만, 개선은 가장 좋은 값보다 규칙만큼 더 좋을 때만 판정합니다.

검토했지만 고르지 않은 방안은 다음과 같습니다.

- 모드를 run의 조건으로 기록하고 모드가 다른 쌍을 `CONDITION_MISMATCH`로 두는 방안: 모드를 나누는 기준(예: 1.3 220 ms)이 기기와 카메라마다 달라서 앱에 일반 규칙으로 넣을 수 없습니다.
- 원인을 알 때까지 launch 지표의 판정을 보류하는 방안: 가장 작은 변경이지만 launch 회귀를 전혀 잡지 못합니다.

### 2. 녹화 지표 3.1·3.6: 기준값을 유지합니다

정상 run끼리 비교할 때의 오탐은 대부분 run 하나를 baseline으로 쓴 데서 왔습니다. 집합 비교에서는 3.6의 오탐이 사라졌고, 남은 오탐은 3.1이 나머지 아홉 run보다 높은 정상 run 하나에서만 나옵니다. 기준값을 넓히면 저조도에서 보이던 작은 신호도 함께 사라지므로, 새 측정에서 오탐률을 다시 본 뒤 정합니다.

### 3. 단일 baseline의 한계: 집합으로 바꿉니다

1번과 같은 변경입니다. `index.json`은 schema 2가 되어 키마다 run id 목록을 저장하며, schema 1 파일의 단일 포인터는 run 하나짜리 집합으로 읽습니다. run 하나짜리 집합의 판정은 v2의 쌍 비교와 같습니다.

### 4. 미탐: 1.9와 1.10을 추가합니다

- **1.9 first open**: 1.1이 warmup으로 버리는 첫 사이클의 open입니다. 다른 앱이 카메라를 쥐고 있으면 이 사이클만 198–275 ms가 됩니다.
- **1.10 open max**: 1.1 측정 사이클의 최댓값입니다. 발열 상태에서 아홉 사이클 중 한두 번이 259–296 ms로 튀는 것을 봅니다.

두 값은 1.1이 이미 저장하는 warmup 표본과 max에서 읽으므로, 두 지표가 생기기 전에 저장된 run도 읽을 때 같은 값을 얻습니다. 그래서 `metric_definition_version`을 올리지 않았고 기존 baseline과 계속 비교됩니다. 점수에는 넣지 않습니다.

## 후보 검토 결과

정상 10회 가운데 3개로 만들 수 있는 집합 120개를 모두 baseline으로 두고, 각 집합에 들지 않은 run과 비교했습니다. 칸은 "저하 판정이 나온 쌍 / 전체 쌍"입니다. 단일 baseline 행은 v2 규칙으로 정상 10회를 하나씩 baseline으로 둔 결과입니다.

| 조건 | 단일 baseline (v2) | 집합 3개 (v2 규칙) | 집합 3개 + 1.9·1.10 (v3) |
|---|---:|---:|---:|
| 정상 | 30/90 (33 %) | 84/840 (10 %) | 84/840 (10 %) |
| 2일차 대조군 | 17/60 (28 %) | 0/720 (0 %) | 0/720 (0 %) |
| 저조도 2단계 | 30/60 (50 %) | 114/720 (16 %) | 114/720 (16 %) |
| 발열 LIGHT | 10/60 (17 %) | 0/720 (0 %) | 360/720 (50 %) |
| 점유 경쟁 | 9/60 (15 %) | 0/720 (0 %) | 720/720 (100 %) |
| 발열 MODERATE | 판정 불가 | 판정 불가 | 판정 불가 |

- 정상 오탐 84쌍은 모두 3.1이고, 3.1이 나머지 아홉 run보다 높은 정상 run 하나가 집합 밖에 있을 때 생깁니다(84 = 그 run을 뺀 9개로 만드는 집합 수).
- 점유 경쟁은 1.9가 모든 쌍에서 잡습니다. 발열 LIGHT는 1.10이 6회 중 3회에서 잡습니다.
- 저조도는 여전히 3.1·3.6의 작은 변화로만 드러나고, 정상 run끼리의 변동과 구별되지 않습니다. 알려진 한계로 남깁니다.
- 발열 MODERATE run은 `THERMAL_HIGH`로 comparison 부적격이므로 설계대로 판정하지 않습니다.
- 집합 크기를 5로 늘리면 정상 오탐률은 같고(3.1, 10 %) 저조도 탐지는 9 %로 줄었습니다. 권장 크기를 3개 이상으로 둔 이유입니다.

단일 baseline의 수치는 [#165 본문](https://github.com/TTolsun/hal-camera/issues/165)과 같은 쌍을 셌습니다. 본문은 baseline의 launch 모드별로 나눠 적었고, 이 표는 합쳤습니다.

재현: [MeasuredBaselineSetTest](../../app/src/test/java/dev/halcamera/benchmark/domain/MeasuredBaselineSetTest.kt)가 [baseline-set-20260926.tsv](../../app/src/test/resources/baseline-set-20260926.tsv)의 40회로 v3 열을 앱의 `RegressionDetector`에 넣어 다시 계산합니다. TSV에는 조건, 원본 JSON의 SHA-256, 7.5의 조건 값, 비교 대상 지표의 값이 있습니다. 원본 JSON 40개는 로컬에 보관합니다.

## 남은 확인

1. 새 빌드로 S25+ camera 0에서 정상 10회와 조건별 6회(저조도 2단계, 발열 LIGHT, 점유 경쟁)를 새로 측정합니다.
2. 정상 run 3개로 집합을 만들고, 위 표와 같은 방식으로 정상 오탐률과 스트레스 탐지율을 계산합니다.
3. 결과에 따라 3.1·3.6의 기준값을 다시 정할지 판단합니다.
4. launch 모드가 바뀌는 원인(CPU 클럭, 카메라 HAL 상태) 계측은 별도 이슈에서 진행합니다.
