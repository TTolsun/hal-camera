# 녹화 중 사진의 망원·Torch·추가 FPS 및 코덱 검증

**Galaxy S25+에서 망원, Camera2 HEVC 30fps, CameraX 60fps, Torch를 사용한 녹화 중 사진 저장을 확인했습니다.** 사진이 있는 9개 조건에서 JPEG 27장과 MP4 9개를 저장했습니다. CameraX의 영상 간격 증가는 기존에 수용한 제약으로 유지합니다. 초광각 CameraX에서 후면 Camera2로 전환한 첫 CLI 요청의 타임아웃은 두 번 재현됐으므로 별도 버그로 분리할 근거를 남깁니다. [#221](https://github.com/TTolsun/hal-camera/issues/221)의 후속 검증 기록입니다.

Flash On/Auto는 현재 Video UI에서 선택할 수 없어 **SKIP**했습니다. Torch는 지속 점등이며 이 두 모드의 검증을 대체하지 않습니다. 이번 기록은 새 기능 구현이나 CameraX 프레임 문제의 수정 결과가 아닙니다.

## 환경과 증거

- 기기는 Galaxy S25+ SM-S936N, Android 16(API 36)이며 검증 날짜는 2026년 10월 6일(KST)입니다.
- 설치 앱은 0.19.0(versionCode 628)입니다. 설치 APK의 SHA-256은 `d931cd07da15bbf6161b007efc3a177c2c74064e54583057ea797c1d9abd0484`이며 [#220 검증 APK](assets/video-snapshot-failures-20261006/build-summary.json)와 일치합니다. APK를 교체하지 않았습니다. 검토한 소스는 `8d2c51f`이며 버전 문자열만으로 바이너리를 식별하지 않습니다.
- 프리뷰 1280×720, 분석 YUV 640×480, JPEG 1920×1080, 영상 1920×1080을 명시했습니다. 녹화 중 사진은 JPEG만 저장합니다. Camera2는 H264 또는 HEVC를 요청했고, CameraX는 Auto를 요청했습니다.
- CLI `preview`로 스트림을 준비하고 UI에서 녹화를 시작했습니다. `record.start`는 실행 중 UI 사진 버튼을 비활성화하므로 사용하지 않았습니다. 사진 버튼을 약 3초 간격으로 세 번 누른 뒤 정지했습니다. 첫 HEVC 30fps 조건은 약 2초 간격입니다.
- 밝은 장면과 어두운 장면은 사용자가 준비했습니다. 조도·차폐·피사체 거리·오디오 조건을 정량 통제하지 않았습니다. 각 조건은 1회이며 통계적 반복 실험이 아닙니다.

원본 영상·사진·화면·앱 PID 로그는 로컬 `reviews/issue221/`에 보관합니다. 저장소에는 픽셀을 넣지 않고 다음 메타데이터만 둡니다.

| 증거 | 내용 |
| --- | --- |
| [media-analysis.json](assets/video-snapshot-combinations-20261006/media-analysis.json) | MP4 13개와 녹화 중 JPEG 27장의 SHA-256, 크기, 실제 코덱, FPS와 모든 긴 간격을 기록합니다. |
| [observations.json](assets/video-snapshot-combinations-20261006/observations.json) | 요청 조건, UI에서 표본으로 관찰한 물리 ID·Flash Fired, 저장 수, 화면 해시와 탭 시각을 기록합니다. |
| [cli-results.json](assets/video-snapshot-combinations-20261006/cli-results.json) | 프리뷰에서 적용한 스트림, 전환 실패·재시도, 이후 일반 사진 촬영과 최종 상태를 기록합니다. |

분석에는 [기존 MP4/JPEG 분석 스크립트](assets/video-snapshot-20261005/analyze.mjs)를 사용했습니다. `mdhd`와 `stts`를 읽고 `ctts`가 있으면 표시 시각을 복원해 정렬합니다. 이번 13개 파일에는 `ctts`가 없었습니다. 긴 간격의 기준은 표시 간격 중앙값의 1.5배 초과입니다. 이 수치는 저장 파일의 시각 정보이며 HAL 내부 손실이나 화면 표시 지연의 직접 측정이 아닙니다.

탭 로그의 `/proc/uptime`은 기기 부팅 뒤의 초 단위 시각입니다. 앱 콜백 시각이나 MP4의 상대 PTS와 같은 원점을 가진다고 가정하지 않습니다. 사진 사이의 입력 간격과 영상의 긴 간격 사이 간격을 대조했지만, 사진 요청을 특정 인코딩 프레임에 직접 결합한 것은 아닙니다.

CameraX 망원 사진 영상은 0초와 6.831초, 9.930초, 12.962초에 긴 간격이 있었습니다. 사진 없는 망원 영상에는 0초의 긴 간격만 있었습니다. 사진 세 번의 입력 간격과 이후 세 간격의 시간차가 대응하며, 이전에 수용한 CameraX 제약과 같은 관찰입니다.

CameraX 60fps 사진 영상의 긴 간격은 0초, 6.486초, 9.570초, 10.720초, 12.654초입니다. 이 중 6.486→9.570→12.654초의 시간차가 세 번의 사진 입력 간격과 가깝지만 10.720초의 추가 간격을 특정 사진과 대응시키지는 못했습니다. 어두운 장면의 사진 없는 영상에도 반복 간격이 있으므로 모든 60fps 간격 증가를 사진 때문에 생겼다고 판단하지 않습니다. 사진 저장과 실제 60fps 계열 포맷을 확인한 범위이며, 영상 연속성을 보장하는 PASS가 아닙니다.

## 망원과 플래시

물리 ID 6은 독립 카메라로 열지 않았습니다. 논리 ID 0에서 3×를 선택하고 Live의 `Phys` 값을 확인했습니다.

| 조건 | 프리뷰에서 관찰한 ID | 녹화 초반·사진 뒤에 관찰한 ID |
| --- | --- | --- |
| 밝은 장면, Camera2 3× | 6 | 6 |
| 밝은 장면, CameraX 새 세션 3× | 6 | 6 |
| 어두운 장면, Camera2 3× | 5 | 5 |
| 어두운 장면, CameraX 3× | 5 | 6 |

CameraX의 첫 밝은 장면 준비에서는 3×에도 ID 5가 관찰됐습니다. 새 세션에서 ID 6을 확인한 뒤 망원 사진 조건을 실행했습니다. 어두운 Camera2 3×는 기본 센서가 유지된 결과로 분류하며 망원 출력 성공으로 합산하지 않습니다. CameraX는 세션이 녹화로 바뀌며 관찰 ID가 달라졌습니다. 표는 UI에서 관찰한 표본이며 모든 JPEG와 인코딩 프레임의 물리 출처를 개별 검증했다는 뜻은 아닙니다.

Video의 플래시 메뉴에는 Off와 Torch만 있었습니다. `LiveControlSupport.flashModes(video=true)`와 `LiveControlBar.bind`도 On/Auto를 Off로 바꾸도록 구현되어 있습니다. 따라서 On/Auto는 현재 앱의 제공 범위 때문에 SKIP했고 HAL의 미지원 판정으로 기록하지 않습니다. 두 엔진의 Torch 조건에서는 선택 아이콘, `Flash Fired`, 실제로 밝아진 피사체와 녹화 지속을 관찰했습니다. 정지 후 프리뷰를 확인하고 새 CLI 준비에서 Torch를 해제했습니다.

## 엔진 전환 타임아웃

초광각 CameraX에서 후면 Camera2로 전환한 첫 CLI 프리뷰가 두 번 실패했습니다. 재현한 문제는 [#224](https://github.com/TTolsun/hal-camera/issues/224)에서 별도로 추적합니다.

| 경로 | 실패 요청 ID | 같은 명령의 성공 재시도 ID |
| --- | --- | --- |
| 초광각 녹화 중 사진 3장·MP4 저장 뒤 전환 | `b1247b43-aecf-4033-9714-da408aaf0262` | `996267a1-f93e-450b-810c-070c0f7b8773` |
| 초광각 프리뷰만 실행한 뒤 전환 | `634692dd-8f50-4b99-a5ab-9f3f70c505b5` | `7132ff5a-8853-41d2-a9ca-eefeb08122cf` |

실패는 약 30초 뒤 `EXECUTION_TIMEOUT / Operation cancelled before capture`로 완료됐습니다. 화면은 `Preview paused · Reconnect Camera in Lab.` 상태였습니다. 재현 두 회를 확보한 뒤 예정한 나머지 전환 세 회는 실행하지 않았습니다. 성공 재시도로 첫 실패를 덮어쓰지 않습니다.

CameraX camera 2가 CLOSED로 바뀌고 surface를 해제하는 앱 PID 로그를 보존했으나 원인을 확정하지 않았습니다. 사진 없는 경로도 실패하므로 녹화 중 사진의 문제라고 단정하지 않습니다. 이 전환 실패는 추가 조합 검증과 분리해 첫 프레임 수신·close(done)·프리뷰 surface 준비 순서를 조사해야 할 버그입니다.

## 검증 범위와 재현

지원 목록을 확인한 뒤 실행한 사진 조건에는 구성 미지원으로 건너뛴 항목이 없었습니다. Flash On/Auto는 위의 앱 제한 때문에 SKIP했습니다. 다른 기기·해상도·코덱 조합, 정량 조도 조건과 모든 프레임의 물리 출처는 미검증입니다. 이번 30fps HEVC 결과로 [이전 HEVC 60fps 관찰](video-snapshot-20261005.md)의 긴 간격이 해결됐다고 주장하지 않습니다.

Torch와 녹화 종료 뒤 CameraX·Camera2의 일반 JPEG 촬영이 각각 성공했고 파일을 회수했습니다. 앱 삭제나 기존 데이터 삭제는 하지 않았습니다. 앱 코드는 변경하지 않았으므로 새 JVM·Android 빌드를 수행하지 않았습니다. 문서 검사는 기기 검증과 별도로 수행합니다.

1. [HAL CAM CLI 스킬](../../skills/halcam-cli/SKILL.md)에 따라 `hello`에서 CLI 허용·권한·잠금 상태를 확인합니다.
2. 엔진별 `streams`를 조회합니다.
3. 다음 예처럼 프리뷰와 영상 조건을 명시합니다. CameraX에서는 `--engine CameraX --codec Auto`를 사용합니다.

```text
preview --camera 0 --engine Camera2 --preview-size 1280x720 --yuv-size 640x480 --jpeg-size 1920x1080 --video-size 1920x1080 --video-fps 30 --codec HEVC
```

4. UI의 Video 모드에서 녹화를 시작합니다. 망원은 3×와 실제 `Phys 6`을 확인하고, Torch는 메뉴에서 선택합니다.
5. 사진 버튼을 세 번 누른 뒤 정지합니다. UI 상태와 새 파일 이름·개수를 기록합니다.
6. ADB로 원본을 PC의 전용 디렉터리에 회수하고 `node docs/validation/assets/video-snapshot-20261005/analyze.mjs <원본_디렉터리>`를 실행합니다.

다음으로 [녹화 중 사진의 실패·정지 경합 검증](video-snapshot-failures-20261006.md)을 확인하세요.
