# App Bokeh 실기기 검증

2026-10-24에 SM-S936N, 후면 카메라 ID 0에서 확인했다. 제조사 Bokeh와 센서 DEPTH16 없이 사물 사진에 배경 흐림을 적용하고 원본을 보존하는 경로를 검증했다. 사진과 화면 캡처는 로컬 검증 자료로만 보관하며 저장소와 PR에 올리지 않는다. OS는 아래 경계 보정 검사 때 기기 속성을 직접 조회한 Android 17(API 37)을 기준으로 기록한다.

## 실기기 결과

| 시나리오 | 관찰 결과 |
| --- | --- |
| Depth → App Bokeh 진입 | 일반 Camera2 Preview 1280×720 + JPEG 1920×1080을 구성했다. 카메라 서비스 덤프의 출력은 PRIVATE와 BLOB 두 개이며 분석 YUV·DEPTH16·입력 스트림이 없었다. |
| 사물 촬영 | 가까운 마우스·책상과 먼 문·수납장이 보이는 장면을 촬영했다. 원본 JPEG 저장 후 편집기가 열렸다. |
| 동일 원본 비교 | 처리용 원본은 EXIF 방향 보정 후 900×1600이었다. 강도 50·100에서 배경 경계와 무늬가 단계적으로 흐려지고 마우스와 가까운 책상은 선명하게 남았다. |
| 깊이·기준면 | 256×256 상대 역깊이 맵에서 책상과 먼 배경이 구분됐다. 먼 배경을 선택하면 추가 흐림이 줄었다. |
| 강도 0 | 실기기 검사에서 처리용 원본과 `Bitmap.sameAs`가 참이었다. JPEG 재인코딩의 무손실을 뜻하지 않는다. |
| 저장 | UI의 Save copy로 Bokeh JPEG·깊이 PNG·JSON을 저장했다. JSON에서 원본 URI, 강도 100, 선택 좌표, 모델 해시, 900×1600 크기를 확인했다. 원본 파일은 유지됐다. |
| 반복 처리 검사 | 같은 원본에 강도 50·80·100을 적용하고 저장한 이미지들을 다시 디코딩했다. `APP_BOKEH_OK`를 받았다. |
| 화면 복귀 | Home 후 Live 복귀 시 같은 원본으로 편집기를 다시 열었다. 매개변수는 기본값으로 돌아갔다. 닫기 후 Photo 전환 시 일반 셔터와 YUV 포함 기본 세션으로 복귀했다. |
| 카메라 변경 | App Bokeh에서 후면 카메라 ID 2로 바꾸면 Photo가 선택되고 일반 셔터·기본 스트림으로 복귀했다. |
| 처리 시간 | 사진 로드·방향 보정·축소·깊이 추론을 합친 관찰값은 332, 533, 541 ms였다. 렌더·JPEG 저장 시간을 포함하지 않으며 성능 보장값이 아니다. |

## 자동 검사와 리뷰

순수 Kotlin 검사에서는 상대 깊이 정규화, 잘못된·평탄한 출력 거절, 전경 보존과 배경 흐림, 전경 색 번짐 억제, 강도 0, 기준면 변경, 일정한 색과 폭 1 이미지를 다룬다. 전체 `testDebugUnitTest`와 `lintDebug`, 앱·검사 APK 빌드를 별도로 실행했다. 기기 검사는 JVM 검사와 구분한다.

코드 리뷰에서 카메라 변경 후 App Bokeh 상태가 남는 경로를 발견해 다른 전용 모드와 함께 해제하도록 수정했다. 모드 종료 시 이전 App Bokeh 안내도 지운다. UI에서 Original 버튼이 줄바꿈되던 문제도 수정했다.

PR UI/UX 리뷰에서는 Live 선택창과 같은 제목·닫기 아이콘·흰색 선택 테두리와 Gallery의 저장 버튼을 재사용하도록 맞췄다. 비교 버튼에 시각·접근성 선택 상태를 추가했고, 저장 대상을 명확히 하려고 Save copy를 Save Bokeh로 바꿨다. 강도를 바꾸면 보케 결과로 돌아간다. 실기기 UI 검사에서 Original→Depth 선택 상태, 접근성 강도 조절 후 Bokeh 전환, 48dp 슬라이더 높이, 공통 닫기 버튼을 확인하고 `APP_BOKEH_UI_OK`를 받았다. 화면 캡처도 확인했다.

글꼴 배율 115%와 200%에서 화면을 확인했다. 200%에서 Original 글자가 잘리는 문제를 발견하여 비교 버튼에 11–13sp 자동 크기 조절을 적용했고, 재검사 화면에서 전체 문구가 보이는 것을 확인했다. 검사 후 기기의 글꼴 배율을 원래 115%로 복원했다.

## 확인 범위와 한계

이번 새 장면은 후면 사물 한 장이다. 다른 기기·전면·인물·역광·반사체·얇은 경계의 품질을 검증한 것으로 해석하지 않는다. 마우스 주변과 가까운 책상은 보존됐지만 책상 뒤쪽 경계처럼 깊이가 바뀌는 곳에는 흐림이 번지는 부분이 있다. 단안 추정과 저해상도 깊이 맵의 한계이며, 정밀한 피사체 마스크나 광학 보케와 같지 않다. 최대 출력 긴 변은 1600픽셀이며 실시간 미리보기 효과는 제공하지 않는다.

## 가는 잎 경계 보정 재검증

같은 날 설치된 main `2157ebe2`에서 촬영한 역광 화분·창밖 건물 사진을 그대로 사용했다. 새 장면을 촬영하거나 강도를 줄여 비교하지 않았다. 개선 전후 모두 처리용 원본 900×1600, 중심 초점 `(0.5, 0.5)`, 강도 100, 같은 MiDaS 모델이다. 기기에서 다시 조회한 `ro.build.version.release=17`, `ro.build.version.sdk=37`을 기록하며, 앞선 Android 16 표기를 정정한다.

| 검사 | 결과 |
| --- | --- |
| 잎 끝 비교 | 원본·개선 전·개선 후를 같은 위치에서 확대했다. 이전에 배경과 함께 흐려지던 잎 끝의 대비가 더 남았다. |
| 잎 영역 수치 | 처리용 원본의 `(180,250)`부터 `(390,420)` 미만 영역에서 원본 밝기 140 미만인 5,321픽셀을 고정해 비교했다. 밝기 평균 절대 오차는 32.81에서 23.11로 약 29.6% 감소했다. 0–255 밝기에서 계산한 이 사진의 국소 비교값이며 일반적인 품질 점수는 아니다. |
| 배경 유지 | 먼 건물의 `(700,80)`부터 `(870,360)` 미만 영역에서 수평 인접 밝기 차의 평균은 원본 3.36, 개선 전 1.23, 개선 후 1.37이었다. 배경 흐림은 유지됐지만 경계 주변 난간 일부는 더 선명해졌다. |
| 기기 처리 | 동일 원본에 강도 0·50·80·100을 적용했다. 강도 0의 `Bitmap.sameAs`와 저장한 이미지 재디코딩 검사가 통과했다. |
| 편집기 | 같은 사진을 편집기에 전달한 기기 검사에서 Original·Depth 전환, 접근성 강도 0·50·100 변경, Bokeh 결과 복귀, Save Bokeh 저장, 닫기를 확인했다. `APP_BOKEH_UI_OK`와 저장 완료 화면을 확인했다. |
| 저장 계약 | UI 저장 JSON의 강도 100, 초점 `(0.5,0.5)`, `renderer=guided_luma_mask_v1`, 결과 900×1600을 확인했다. 깊이 PNG는 256×256이며 원본 JPEG의 SHA-256은 전후 동일했다. |
| 시간 | 첫 처리 검사에서 로드·추론 950 ms, 강도 50·100 렌더 2264·1776 ms를 관찰했다. UI 검사 로드·추론은 608 ms였다. 단일 기기의 관찰값이며 저장 시간이나 성능 보장값이 아니다. |

이번 비교는 저해상도 깊이 경계를 원본 밝기로 보정한 효과를 확인한다. 깊이가 잘못된 아주 가는 잎 끝은 일부 여전히 흐려지며, 밝기가 비슷한 경계나 다른 기기·인물 머리카락까지 검증한 것은 아니다. 공개 회귀 검사는 밝고 어두운 가는 전경, 분리된 배경 무늬의 흐림, 보호한 전경의 픽셀 동일성, 일정한 깊이 가중치에서의 무늬 전이 방지, 폭·높이 1과 평탄한 밝기를 다룬다.

처리·모델·스트림 계약은 [App Bokeh 설계](../design/APP-BOKEH.md)에 있다.
