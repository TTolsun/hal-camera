`app/src/main/java/dev/halcamera/benchmark/RunValidity.kt` (rule version `validity-v1`). Answers three separate questions about a run instead of one, per `PLAN-BenchMarker-v0.3.md` 5.3: is the measurement valid, may it be compared, may it feed a cross-device score.

Thirteen `ValidityFlag`s each declare which of the three they block, and the flags are grouped by that answer. ABORTED, HARD_FAILURE, PROFILE_UNSUPPORTED and INSUFFICIENT_SAMPLES block everything: the run does not contain what the profile promised. CADENCE_NOT_FIXED, THERMAL_HIGH and POWER_SAVE_MODE block comparison and scoring: measured correctly, but not against anything else. CHARGING, BATTERY_LOW and PROFILE_DRAFT block scoring only: usable in-house, excluded from a cross-device number. PREFLIGHT_MISMATCH, THERMAL_CHANGED and LABEL_MISSING are informational.

The three booleans are always derived from the flag table, never set by hand, and they cascade — comparison requires measurement, scoring requires comparison. `fromJsonMap` re-derives them from the stored flag *codes* and never trusts the stored booleans, so a change to the table applies consistently to old files. Codes this app version does not recognise are kept verbatim in `unknownFlags` and treated fail-closed: they block comparison and scoring, because the flag may have been a blocking one in the version that wrote it. `ruleVersion` is stored in every run so a reader knows which table produced the booleans.

`RunValidityEvaluator.flags` holds the thresholds: thermal at MODERATE or above, battery below 20 %, fewer than 15 observed frames. The thermal check uses the run-wide peak rather than the start value, with the reason recorded inline — starting LIGHT and ending SEVERE is not a comparable run.
